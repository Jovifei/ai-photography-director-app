## 2. OS 进程死亡验证方法

### 为什么不能用 Activity recreation 代替

`ActivityScenario.recreate()` 只证明 Activity 生命周期重建；它不证明应用进程、静态对象、Room 实例和启动路径在 OS 终止后重新初始化。因此 P23D 把 prepare 和 verify 分成两个独立的 instrumentation invocation：

1. `cleanup-before` 清理测试 fixture；
2. `prepareProviderReadySummaryState_forExternalForceStop` 写入 Provider READY、summary、primary 和 last-active；
3. 外部脚本显式启动 `MainActivity`，用 PID 检查确认进程存在；
4. 执行 `adb -s <dedicated-emulator> shell am force-stop com.jovi.photoai`；
5. 再次读取 PID，只有进程确实消失才记录 `PASS_OS_PROCESS_TERMINATED`；
6. 新 instrumentation invocation 执行 `verifyProviderReadySummaryState_afterExternalOsProcessRestart`，该方法先启动真实 `MainActivity`，再通过生产 Repository/Flow 读取恢复结果；
7. `cleanup-after` 删除合成数据。

脚本 `scripts/qualify_p23d_ready_recovery.ps1:45-58` 对 `pidof` 使用专用探测：Android toybox 在进程不存在时通常返回 exit 1，这是 force-stop 后的预期状态，不应被通用严格 ADB wrapper 当成设备故障。其它 PID 探测错误仍然阻断。脚本只接受 `emulator-数字`，并验证 `ro.kernel.qemu=1` 与 SDK 35；所有 ADB 均显式带 serial。

### 实际证据边界

本轮 P23D runner 为 `3/3` 方法通过，prepare、启动、force-stop、PID 消失、verify、cleanup 全部 PASS。测试使用程序生成内容，不读取私人照片、不启动 Qwen/LAN、不访问 Pipeline、不修改防火墙，也不触碰实体设备。

## 3. 一次真实测试源码失配的处理方式

P23D 初始源码把生产 `ProjectSummaryRequest` 的命名参数写成了 `readyInputs`，而生产 API 定义的是 `readyItems`。这导致首次 `assembleDebugAndroidTest` 在编译阶段失败；错误是测试源码与当前生产 API 失配，不是设备或签名环境问题。

修复原则：

- 只修正两处测试调用的命名参数；
- 不为了兼容旧测试而增加无 token/旧签名绕过入口；
- 修复后重新编译 Debug/Test APK，再执行完整 P23D、P23C、R1 和既有 Android 回归；
- 源码变更先提交，再从真实 Git object 重新生成 manifest。

## 4. Git object 清单与 Windows 哈希域

Windows `core.autocrlf` 可能使工作树 CRLF 字节与 Git blob 字节不同。可复用规则：

1. manifest 的 `source_commit` 必须先绑定实际源码提交；
2. 对每个 `source_commit:path` 使用 `git rev-parse` 校验 blob OID；
3. 使用 `git cat-file blob` 读取 canonical Git bytes，计算字节数和 SHA-256；
4. 不使用 Windows 工作树 CRLF SHA-256 替代 Git source hash；
5. 报告中明确 hash domain，避免把换行规范化差异误判为源码漂移。

P23D manifest 的两个源文件均通过 OID、字节数和 SHA-256 复核；外部 emulator 日志和原始证据不进入仓库。

## 5. Dirty Owner 主树的安全合入经验

Owner 主工作树当时位于 `main`，有 18 项既有修改/未跟踪文件，并且本地分支落后远端。安全步骤是：

1. 在仓库外保存 Owner 相对路径、大小和 SHA-256 快照；
2. fetch 后以真实 `origin/main` 和候选远端 SHA 为准；
3. 新建 linked worktree，不在 Owner 主树执行 pull、reset、stash、clean 或 checkout；
4. 从当前 `origin/main` 创建 landing 分支，对候选执行 `git merge --ff-only`；
5. 在 landing worktree 重新执行 Debug/Test/JVM/Lint（签名 guard 外）、privacy 和 diff 检查；
6. push 前再次 fetch，确认 `origin/main` 未发生竞态；
7. 只用普通 fast-forward push 更新 `main`；
8. 合入后核对 `origin/main == reviewed candidate SHA`，Owner 主树仍保持原始 dirty 状态。

这套流程的关键不是“把 Owner 本地树更新到最新”，而是把用户未提交文件与远端合入动作隔离。Owner 本地树后续若要同步 main，必须由 Owner 单独处理潜在冲突，不能自动覆盖其文件。

## 6. Gate 语义不能混用

- `assembleDebug`、AndroidTest、JVM、Lint 通过，只能证明无签名静态/测试构建通过。
- `verifyReleaseSigning` 缺少 `PHOTOAI_RELEASE_STORE_FILE` 时必须保留 `BLOCKED`，不能生成新生产密钥，也不能把 `-x verifyReleaseSigning` 的结果写成签名 PASS。
- 合成 Provider、模拟器和合成 JPEG 证明的是状态机与恢复链，不是真实照片质量或真实 Provider 运行。
- 独立审查 PASS 绑定精确 SHA；main 合入是另外一个明确授权动作。
- `NOT_RUN` 必须保留：真实照片、Qwen/LAN、Pipeline、Cloud、iOS、实体设备、公开发布及未提供的签名材料。
