# PKB1 producer golden-vector handoff request

Status: `PENDING_EXTERNAL_GOLDEN_VECTORS`. This is a consumer-side request prepared for the Nightly Photo Intelligence producer team. It does not establish T14 compatibility or authorize automatic transfer, sibling-repository access, real-photo acquisition, service activation, or a producer release.

## Frozen consumer inputs

Use [Photo Knowledge Bundle Consumer v1](reference/PHOTO_KNOWLEDGE_BUNDLE_CONSUMER_V1.md), its [schema](reference/photo_knowledge_bundle_consumer.v1.schema.json), and the Android parser/digest implementation in `android/app/src/main/java/com/jovi/photoai/data/reference/PhotoKnowledgeBundle.kt`. T13 replacement policy is defined by `KnowledgeBundleReplacement.kt` and enforced atomically by `ReferenceRepository.replaceKnowledgeBundle`.

The selected document is strict UTF-8 JSON without BOM, at most 512 KiB. Root fields are exactly `contract_version`, `bundle_id`, `source`, `integrity`, `references`; version is `1.0`. `source` contains exactly `origin` (`PIPELINE` or `LOCAL_SERVICE`), `producer_id`, `release_id`. `integrity` contains exactly `algorithm` (`SHA-256`) and `payload_sha256`. Each of 1–20 references contains exactly `reference_id` and `photography`; reference IDs are unique.

Photography fields are exactly `scene`, `background_story`, `lighting`, `composition`, `subject_intent`, `emotion`, `pose_template`, `camera_position`, `director_prompt`. All are nonblank single-line text without ISO controls or transport/path-like content. Limits are 800 Unicode code points per field and 1,200 for `director_prompt`. Opaque identifiers match `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`. IDs must not derive from private photos, filenames, URIs, EXIF, media hashes, accounts, devices or location. No model metadata, provider credentials, images, keypoints, databases or private assets belong in these vectors.

## Requested producer-generated deliverables

Deliver a versioned manifest and the exact raw UTF-8 bytes of each JSON vector, plus its byte length and SHA-256 of the complete raw document. Preserve these files byte-for-byte; do not paste and reserialize them. Separately provide the declared and independently computed PKB1 payload digest, expected consumer parser result, producer source revision, vector-generation command and runtime version. Distinguish raw-document SHA-256 from `integrity.payload_sha256`: the latter hashes the canonical PKB1 payload, not JSON bytes.

| Vector | Required behavior and evidence |
| --- | --- |
| Valid single-reference | One synthetic reference with all fields and explicit local mapping example; include Chinese text to exercise UTF-8 byte lengths. |
| Valid multi-reference | At least two distinctive synthetic references, deliberately nontrivial array order and explicit producer-ID to app-local-ID mapping. No order-based association. |
| Replacement A and B | Same bundle ID, producer ID, origin and producer reference IDs; distinct opaque release IDs, distinctly different composition and director prompt, independently computed canonical digests. Document the frozen old provenance tuple required at confirmation. |
| Repeated identical release | Same release and payload: expect `REPLACEMENT_ALREADY_APPLIED`, with no mutation. |
| Conflicting same release | Same release but changed guidance and a correctly recomputed digest: expect `REPLACEMENT_IDENTITY_CONFLICT`, with no mutation. |
| Changed association | Changed bundle/producer/origin/reference association: parser validity is distinct from replacement eligibility; expect replacement refusal. |
| Invalid schema | Unknown or missing field, duplicate JSON key, wrong field type, unsupported version, duplicate reference ID and zero/over-20 references; include expected error for each. |
| Invalid text/encoding | BOM, malformed UTF-8, blank/multiline/control-containing or overlimit guidance and transport/path-like text. Include exact binary bytes for malformed encoding. |
| Invalid integrity | Guidance mutation with old digest, invalid algorithm and malformed digest. No READY result, fallback Demo or partial writes. |

For replacement, the expected old tuple is `{bundleId, producerReferenceId, producerId, origin, releaseId, payloadSha256, importedAtEpochMillis}` keyed by exact app-local reference ID. The timestamp is app-local receipt evidence, supplied by a fresh read of the existing record, not guessed or generated by the producer. Map every producer reference ID explicitly to an existing reference in one project. A stale tuple must fail closed. Release identifiers are opaque; no lexical or numeric “newer release” inference is permitted.

## Canonical bytes required for interoperability

Supply canonical-byte fixtures or their exact hexadecimal representation alongside the JSON vectors. PKB1 starts with ASCII `PKB1\n`. Every ordered field name and value is a separate token encoded as decimal UTF-8 byte length, ASCII `:`, raw UTF-8 bytes, ASCII newline. The frozen field order is contract version, bundle ID, source origin/producer/release, reference count, then each array element's reference ID and the nine photography fields in schema order. Preserve array order. Exclude the integrity object. No Unicode normalization, trimming, escaping, locale conversion or newline conversion is applied to token values. Never substitute JSON serialization, JSON canonicalization or a media hash for this algorithm.

The receiver must verify complete raw-document hashes before reading vectors, strict-decode their preserved bytes, and compare official consumer PKB1 recomputation with producer canonical bytes/digests. Negative vectors must preserve their intentional invalid bytes and expected error codes. A successful synthetic App-only test or locally generated A/B vector is not producer compatibility evidence.

The exact canonical names are `contract_version`, `bundle_id`, `source.origin`, `source.producer_id`, `source.release_id`, `references.count`, followed for each zero-based index `i` by `references[i].reference_id` and `references[i].photography.scene`, `.background_story`, `.lighting`, `.composition`, `.subject_intent`, `.emotion`, `.pose_template`, `.camera_position`, `.director_prompt` (each abbreviated suffix retains the full `references[i].photography` prefix). A schema object's JSON key order is not the canonical order.

Use one intentional defect per negative vector so validation order is unambiguous. Frozen examples: extra/missing key or duplicate JSON key → `SCHEMA_INVALID`; unsupported string version → `VERSION_UNSUPPORTED`; duplicate reference ID → `DUPLICATE_REFERENCE_ID`; invalid UTF-8 or BOM → `INVALID_UTF8`; unsafe/blank/overlimit text or malformed digest → `FIELD_INVALID`; valid guidance mutation with old digest → `DIGEST_MISMATCH`; invalid algorithm or 0/21 references → `SCHEMA_INVALID`; malformed JSON syntax → `MALFORMED_JSON`; over-512-KiB document → `DOCUMENT_TOO_LARGE`. Wrong-type vectors must name the exact field and the implementation-derived error rather than assume all types share one code.

## Acceptance and handoff receipt

Return a manifest identifying every file and expected result, exact producer revision, independent generation evidence, explicit mappings and authorization/provenance for synthetic-only data. The consumer will record exact App revision, vector raw hashes, parser/digest outcomes, explicit mapping/import/replacement outcomes, and no-write rejection evidence. Only completed producer-generated vector qualification can change T14 from pending to machine validated. Physical photography quality, human review, legal/artifact authority and production release remain separate gates.
